## 학습 목표와 순서 (Goals and Outline)

- **목표 1**: 엣지 장치에서 모델 파일과 실행 데이터가 노출되는 경로 설명
- **목표 2**: 저장 암호화와 모델 코드 변환이 막는 위협과 막지 못하는 위협 구분
- **목표 3**: 장치에 맞는 런타임과 연산 커널을 선택하고 보호 계층 조합

| 순서 | 핵심 질문 |
| :--- | :--- |
| 배경 | 장치에 배포·실행되는 모델의 형태 |
| 위협 | 공격자가 얻거나 바꿀 수 있는 자산 |
| 대응 | 암호화·코드 변환·런타임 선택이 바꾸는 것 |
| 한계 | 실행 중에도 남는 위험과 필요한 통제 |

> **전제**: 공격자가 엣지 장치에 물리적으로 접근할 수 있는 상황

## 엣지 AI란 (Edge AI)

<!-- IMAGE [비교도식] 클라우드 추론과 엣지 추론의 데이터 흐름 비교 (img/17-edge-vs-cloud.png) -->

- **추론**(Inference): 학습이 끝난 모델에 새 입력을 넣어 결과를 계산하는 과정
  - 예: 카메라 영상 한 장을 모델에 넣어 "사람 있음" 판정
- **클라우드 추론**: 입력 데이터를 서버로 보내고 서버가 계산한 결과를 받음
- **엣지 추론**: 데이터가 생기는 현장의 장치(예: 라즈베리파이 카메라 노드)가 직접 모델을 실행

| 관점 | 클라우드 추론 | 엣지 추론 |
| :--- | :--- | :--- |
| 지연·연결 | 네트워크 왕복 시간과 연결 상태에 영향받음 | 네트워크 없이 추론 가능 |
| 개인정보 | 입력이 장치 외부로 전송될 수 있음 | 입력을 장치 내부에 둘 수 있음 |
| 운영 | 서버·통신 운영 필요 | 장치의 전력·메모리·성능에 제약 |
| 모델 위치 | 서비스 서버에 보관 | 장치의 저장장치·메모리에 존재 |

> **엣지의 장점과 과제**: 데이터를 장치에서 처리할 수 있지만, 모델이 공격자가 만질 수 있는 장치에 놓임

## 모델 배포 방식 (Deployment Forms)

| 방식 | 장치에 배포되는 것 | 주요 분석 대상 |
| :--- | :--- | :--- |
| 파일 기반 | `.tflite`, `.onnx` 모델 파일과 런타임 | 모델 파일과 실행 중 메모리 |
| 코드/AOT 변환 | 모델 상수·연산이 포함된 라이브러리·실행 파일 | 실행 파일과 실행 중 메모리 |

- **런타임**: 모델 파일을 읽어 연산을 순서대로 실행하는 라이브러리(예: TensorFlow Lite 인터프리터, ONNX Runtime)
- **AOT**(Ahead-Of-Time) **변환**: 실행 전에 모델을 대상 CPU용 기계어로 미리 컴파일하는 방식
- **파일 기반의 특징**: 모델 파일만 바꿔 갱신하기 쉽지만, 공격자도 파일을 직접 열어 분석할 수 있음
- **코드 변환의 특징**: 배포 형태와 분석 비용이 바뀔 뿐, 가중치를 암호화하지는 않음
- **공통점**: 두 방식 모두 입력·출력과 추론 결과가 같을 수 있음

## 모델 배포 방식 (Deployment Forms) (Cont'd)

### 대표적인 모델 파일 형식

- **`.tflite`**: TensorFlow Lite(2024년 LiteRT로 개명) 모델 형식
  - FlatBuffers 직렬화 형식이며 파일 4~7번째 바이트에 식별자 `TFL3` 저장
- **`.onnx`**: ONNX(Open Neural Network Exchange) 모델 형식
  - Protocol Buffers 직렬화 형식이며 PyTorch·TensorFlow 등 여러 프레임워크가 내보내기 지원
- **가중치**(Weight): 학습으로 정해진 모델의 수치 매개변수
  - 예: 합성곱 층의 필터 값, 완전 연결 층의 행렬 원소
- **텐서**(Tensor): 모델의 입력·출력·가중치를 담는 다차원 배열
  - 예: 224×224 컬러 이미지 입력은 형상 `[1, 224, 224, 3]`의 텐서

## 위협 모델과 보호 자산 (Threat Model)

- **위협 모델**: 공격자가 할 수 있는 일과 보호할 자산을 먼저 정해 두는 보안 설계의 전제

| 공격자 능력의 예 | 위협받는 자산 |
| :--- | :--- |
| 저장 매체 복사·수정 | 모델 파일, 설정, 업데이트 패키지 |
| 프로세스·디버거 접근 | 가중치, 중간 활성값, 입력·출력 |
| 추론 API 반복 호출 | 모델 기능과 일부 학습 정보 |
| 장치 소프트웨어 교체 | 모델 무결성, 서비스 가용성 |

- **활성값**(Activation): 각 층의 연산 결과로 다음 층에 전달되는 중간 텐서
- **기밀성**: 모델 구조·가중치가 허가 없이 유출되지 않음
- **무결성**: 모델이나 실행 파일이 바뀌면 탐지·차단함
- **가용성**: 장치와 추론 서비스가 정상적으로 동작함

## 모델 파일이 드러내는 정보 (Model File Contents)

| 형식 | 파일에서 확인할 수 있는 정보 |
| :--- | :--- |
| `.tflite` | 그래프, 연산자, 텐서 형상과 타입, 양자화 정보, 상수 버퍼(가중치) |
| `.onnx` | 노드, 연결, 연산자 집합(opset), 텐서 이름과 형상, initializer(가중치) |
| 부가 자료 | 라벨 목록, 전처리 설정 등이 별도 파일로 배포될 수 있음 |

- **양자화**(Quantization): 32비트 실수 가중치를 8비트 정수 등으로 바꿔 크기와 연산량을 줄이는 기법
  - 원래 값을 되돌리는 데 필요한 scale·zero point가 파일에 함께 저장됨
- **initializer**: ONNX 그래프에 상수로 저장된 텐서이며, 가중치가 여기에 들어 있음
- **Netron**: 모델 파일을 열어 그래프 구조와 각 텐서 값을 보여 주는 시각화 도구
- **외부 데이터**: ONNX는 큰 가중치를 모델 파일 외부의 별도 파일에 저장하도록 구성할 수도 있음

## 모델 파일이 드러내는 정보 (Model File Contents) (Cont'd)

### 모델 유출과 학습 데이터 유출의 구분

- **모델에 없는 것**: 원본 학습 데이터 전체가 그대로 들어 있지는 않음
- **모델 추출**(Model Extraction): 파일 복사나 반복 질의로 원본과 같은 기능의 모델을 얻는 공격
- **모델 역전**(Model Inversion): 모델 출력이나 가중치로부터 학습 데이터의 특징을 복원하는 공격
  - 예: 얼굴 인식 모델에서 특정 인물의 대표 얼굴 이미지를 재구성
- **멤버십 추론**(Membership Inference): 특정 데이터가 학습에 쓰였는지를 모델 출력으로 추정하는 공격
- **평가 원칙**: 세 공격은 필요한 능력과 피해가 다르므로 서로 다른 위협으로 평가

## 오프라인 모델 노출 경로 (Offline Exposure)

- **오프라인 공격**: 장치가 꺼진 상태에서 저장 매체만 떼어 내 분석하는 공격
- **저장 매체 복사**: SD 카드를 PC에 꽂아 ext4 파티션의 모델 파일을 그대로 복사
  - 예: `/home/<user>/app/model.tflite`를 복사해 PC에서 Netron으로 열람
- **권한·백업**: 서비스 계정의 권한이 과도하면 다른 프로세스가 모델 파일을 복사
- **운영 산출물**: 이미지 백업, 로그, 디버그 패키지에 모델 파일이 함께 포함

> **주의**: 모델을 숨겨진 경로에 두는 것만으로는 보호되지 않으며, 파일 접근 권한과 배포·백업 경로를 함께 점검

---

## 모델 변조와 지식재산 (Integrity and IP)

- **변조 조건**: 저장 매체 쓰기 권한을 얻으면 공격자가 모델 파일을 교체할 수 있음
  - 항상 "사람 없음"을 출력하는 모델: 감시 기능 무력화
  - 항상 경보를 출력하는 모델: 오경보로 인한 서비스 거부
- **변조 탐지**: 배포 시 모델의 SHA-256 해시에 서명해 두고, 로드 전에 해시를 다시 계산해 비교
  - 검증이 없으면 바뀐 모델도 정상 모델처럼 로드됨
- **지식재산**: 직접 학습한 모델의 구조와 가중치는 연구개발 자산
- **유출 범위**: 모델 유출이 원본 학습 데이터 전체의 유출을 뜻하지는 않음

> **구분**: 기밀성 보호(유출 방지)와 무결성 보호(변조 탐지)는 별개의 목표이며 각각 다른 통제가 필요

## 저장 암호화의 효과와 조건 (Encryption at Rest)

- **저장 암호화**: 저장 매체에 기록된 데이터를 암호화된 상태로 보관하는 방식
  - 예: Linux의 LUKS로 모델이 들어 있는 파티션 전체를 암호화
- **효과**: 장치가 꺼져 있고 복호화 키가 없는 공격자의 **오프라인 파일 복사**를 무력화
- **키 보관 문제**: 키를 모델과 같은 SD 카드에 평문으로 저장하면 공격자가 키도 함께 복사
- **키 보호 수단**: 장치가 부트 체인 검증, 보안 요소, 하드웨어 키 저장소를 지원하는지 확인
  - **부트 체인**: 부트로더 → 커널 → 애플리케이션 순서로 다음 단계의 서명을 검증하며 실행하는 과정
  - **보안 요소**(Secure Element): 키를 칩 외부로 꺼낼 수 없게 보관하는 전용 보안 칩(예: Microchip ATECC608)

---

## 저장 암호화의 효과와 조건 (Encryption at Rest) (Cont'd)

### 암호화와 변조 탐지

- **한계**: 암호화만으로는 변조를 탐지할 수 없음
  - 예: AES-CTR로 암호화한 파일의 바이트를 바꾸면 복호화 결과도 오류 없이 바뀐 값이 됨
- **AEAD**(Authenticated Encryption with Associated Data): 암호화와 변조 검사를 함께 수행하는 인증 암호
  - 예: AES-GCM은 복호화할 때 인증 태그가 맞지 않으면 실패를 반환
- **전자서명**: 개인키로 서명하고 공개키로 검증하여 배포 패키지의 출처와 무결성을 확인하는 방식
  - 예: 제조사가 Ed25519 개인키로 모델 패키지에 서명하고 장치는 내장 공개키로 검증
- **공개키 관리**: 장치에 내장한 공개키를 공격자가 바꿀 수 있으면 서명 검증도 무력화됨

## 추론 중 메모리 노출 (Runtime Exposure)

- **평문 사용**: 런타임은 추론을 위해 모델과 가중치를 복호화된 상태로 메모리에 올려 사용
- **평문이 나타나는 위치**: 입력 버퍼, 가중치·활성값 텐서, 프로세스 메모리
- **보호 대상**: 가중치 외에 중간 활성값, 입력·출력, 복호화 키
- **코어 덤프**: 프로세스가 비정상 종료될 때 메모리 내용을 파일로 저장한 것이며, 평문 가중치가 포함될 수 있음
- **스왑**: 메모리가 부족할 때 메모리 페이지를 저장장치로 옮기는 기능이며, 평문이 SD 카드에 기록될 수 있음
- **루트·디버거 권한**: 실행 중인 프로세스의 메모리를 직접 읽을 수 있음(예: `gdb`로 연결해 메모리 덤프)

---

## 추론 중 메모리 노출 (Runtime Exposure) (Cont'd)

### 보호 범위

- **저장 암호화**: 꺼진 장치에서 파일을 복사하는 위험을 줄임
- **실행 중 장치**: 공격자가 루트 권한을 얻으면 메모리의 평문에 접근하는 위험이 남음
- **덤프 제한**: 프로세스가 `prctl(PR_SET_DUMPABLE, 0)`을 호출
  - 효과: 코어 덤프를 만들지 않고, 일반 사용자 권한의 디버거 연결도 거부
- **신뢰 실행 환경**(TEE, Trusted Execution Environment): 일반 OS와 격리된 CPU의 보호 실행 영역
  - 예: Arm TrustZone 기반 OP-TEE
- **TEE의 한계**: 부채널 공격과 출력 기반 공격까지 자동으로 막지는 않음
- **부채널 공격**: 실행 시간·전력 소비처럼 연산의 부수 정보로 비밀을 알아내는 공격

## 모델을 코드로 변환 (Model to Code)

<!-- IMAGE [파이프라인] TVM 컴파일 파이프라인 - ONNX→Relay IR→최적화→타깃 코드 생성 (img/26-tvm-pipeline.png) -->

- **Apache TVM**: 모델 그래프를 대상 하드웨어용 실행 코드로 변환하는 오픈 소스 딥러닝 컴파일러
- **IR**(Intermediate Representation): 컴파일러가 최적화를 위해 사용하는 프로그램의 내부 표현

1. ONNX·TFLite 등의 모델을 IR로 변환
2. 연산 그래프를 최적화하고 대상 CPU에 맞는 연산 구현을 선택
3. 기계어 라이브러리, 그래프, 상수를 생성하거나 하나의 AOT 모듈로 생성

- **가중치 위치**: 설정에 따라 생성된 라이브러리 내부 또는 별도 데이터 파일에 저장
- **연산 융합**(Operator Fusion): 합성곱 + ReLU처럼 연속된 연산을 하나의 함수로 합치는 최적화
  - 융합 후에는 원본 그래프의 층 구조가 코드에 그대로 드러나지 않음
- **타깃 의존성**: 실행 파일 크기, 런타임 의존성, 지원 연산자가 대상 하드웨어와 설정에 따라 다름

---

## 코드 변환이 바꾸는 것 (Effect of Code Conversion)

| 관점 | 평문 모델 파일 | 저장 암호화 | C/C++·AOT 변환 |
| :--- | :--- | :--- | :--- |
| 오프라인 분석 | 파일을 파싱해 구조·가중치 확인 | 키가 없으면 파일 분석 방해 | 바이너리 분석·역공학 필요 |
| 실행 중 메모리 | 런타임 텐서가 존재 | 추론 시 복호화된 데이터 존재 | 상수와 중간값이 메모리에 존재 |
| 변조 | 파일 교체 가능 | 인증 없이는 변조 탐지 불가 | 서명·검증 없이는 교체 가능 |
| 보안 효과 | 보호 없음 | 저장 상태의 기밀성 향상 | 즉시 분석을 어렵게 해 추출 비용 상승 |

- **역공학**(Reverse Engineering): 실행 파일을 역어셈블·분석해 원래의 구조와 데이터를 알아내는 작업

> 코드 변환은 **암호화가 아니며**, 구조와 가중치를 복구하는 데 필요한 비용을 높이는 수단

---

## C 배열 변환은 암호화가 아님 (C Array Is Not Encryption)

- **`xxd -i`**: 파일의 바이트를 C 배열 소스 코드로 출력하는 명령

```bash
xxd -i model.tflite > model_data.h
# unsigned char model_tflite[] = {
#   0x1c, 0x00, 0x00, 0x00, 0x54, 0x46, 0x4c, 0x33, ...   <- 0x54 0x46 0x4c 0x33 = "TFL3"
# };
# unsigned int model_tflite_len = 80;
```

- **변환 결과**: 모델 바이트를 16진수 리터럴로 다시 적은 것이며 값은 그대로임
- **배열 위치**: `const`가 없는 `unsigned char` 배열이므로 실행 파일의 `.data` 섹션에 그대로 저장됨

---

## C 배열 변환은 암호화가 아님 (C Array Is Not Encryption) (Cont'd)

### 실행 파일에서 모델 바이트 확인

```bash
aarch64-linux-gnu-g++ -O2 app.cc -o app      # app.cc includes model_data.h
aarch64-linux-gnu-objdump -t app | grep model_tflite
# 0000000000011010 g     O .data  0000000000000050  model_tflite
aarch64-linux-gnu-strip app                  # Remove the symbol table
strings -n 4 app | grep TFL3                 # Bytes are still in the binary
# TFL3
```

- **심볼이 있을 때**: `objdump -t`로 배열 이름(`model_tflite`)과 위치(`.data`), 크기(`0x50` = 80바이트)를 바로 확인
- **`strip` 후**: 심볼 이름은 사라지지만 `TFL3` 식별자와 가중치 바이트는 그대로 남음
- **이름 변경의 한계**: 파일 이름·확장자·심볼 이름을 바꾸는 것은 기밀성 대책이 아님
- **AOT 기계어**: 가중치가 기계어의 상수로 들어가므로 바이너리·실행 메모리 분석으로 복구 가능

---

## 자체 런타임 구현의 타당성 (Custom Runtime)

- **전체 구현의 부담**: 연산자, 양자화, 메모리 관리, 오류 처리, 정확도를 모두 직접 검증해야 함
- **우선 검토**: 기존 런타임 사용, 또는 필요한 연산자만 등록하는 **축소 구성**
  - 예: TensorFlow Lite Micro의 `MicroMutableOpResolver`에 모델이 쓰는 연산자만 등록
- **전용 실행기가 타당한 경우**: 모델과 연산자가 고정되고 메모리·저장 공간 제약이 큰 제품

| 선택지 | 적합한 상황 | 부담 |
| :--- | :--- | :--- |
| 기존 런타임 | 모델·연산자 변경이 잦음 | 실행 파일 크기와 의존성 |
| 런타임 축소 | 기존 런타임의 기능은 충분하나 자원이 제한됨 | 구성·빌드 검증 |
| 전용 실행기 | 고정 그래프, 엄격한 자원 제약 | 구현·검증·유지보수 |

---

## 런타임과 연산 커널 (Runtime and Kernels)

| 구성 요소 | 역할 | 예 |
| :--- | :--- | :--- |
| 런타임 | 모델 로드, 그래프 순서대로 실행, 텐서 메모리 관리 | TensorFlow Lite Micro |
| 커널 | 합성곱·행렬곱 등 개별 연산의 최적화 구현 | XNNPACK, CMSIS-NN |

- **커널**(Kernel): 하나의 연산을 특정 CPU에서 빠르게 계산하는 함수(운영체제 커널과 다른 의미)
  - 예: Cortex-A의 NEON SIMD 명령으로 int8 합성곱을 계산하는 함수
- **XNNPACK·CMSIS-NN의 범위**: 모델 파일(`.tflite`, `.onnx`)을 읽는 기능이 없어 단독으로는 모델을 로드할 수 없음
- **모델 실행에 추가로 필요한 것**: 모델 파서, 그래프 실행기, 텐서 메모리 계획
- **커널을 직접 연결할 때**: 지원 연산·데이터 형식과 미지원 연산의 대체 경로 확인

---

## XNNPACK 기반 구성 (Arm Cortex-A)

1. 모델의 연산자·데이터 형식을 확인하고 대상 장치에서 정확도 검증
2. TensorFlow Lite·ONNX Runtime 등에서 XNNPACK 백엔드를 켜는 구성부터 검토
3. 더 작은 구성이 필요하면 XNNPACK API로 고정 그래프를 직접 구성
4. 실행 파일 크기, 추론 지연 시간, 메모리 사용량을 실제 장치에서 측정

- **지원 CPU**: ARM, x86, WebAssembly, RISC-V용 신경망 연산 구현을 제공하는 라이브러리
- **연산자 API**: 연산 하나씩 호출하며, 그래프 실행 순서와 텐서 메모리 관리는 직접 구현
- **Subgraph API**: `xnn_create_subgraph()`로 연산 그래프를 정의
  - `xnn_create_runtime_v2()`로 만든 런타임이 실행 순서와 메모리 계획을 담당
- **남는 위험**: 가중치를 실행 파일에 포함해도 바이너리·실행 중 메모리 분석 위험은 남음

---

## CMSIS-NN 기반 구성 (Arm Cortex-M)

1. 모델을 int8 등으로 양자화하고 CMSIS-NN 지원 연산·데이터 형식과 맞는지 확인
2. CMSIS-NN 커널을 연결한 TensorFlow Lite Micro를 기본 구성으로 사용
3. 더 작은 구성이 필요하면 고정 그래프, 필요한 연산자, 미리 계획한 텐서 메모리로 구성
4. 기준 구현과 출력·정확도·메모리 사용량을 실제 Cortex-M 보드에서 비교

- **CMSIS-NN**: Arm Cortex-M용 신경망 커널 모음이며, 추론 런타임 전체를 제공하지 않음
- **양자화 규격**: TensorFlow Lite for Microcontrollers의 int8·int16 양자화 규격을 따름
- **미지원 연산**: 대체 구현이 필요하며, 빌드 옵션에 따라 실제로 선택된 커널을 확인
- **수치 검증**: 정수 양자화와 커널 최적화로 생기는 출력 차이를 테스트 데이터로 확인

---

## 런타임 선택과 검증 순서 (Selection and Validation)

1. **장치와 위협 정의**: Linux 기반 Cortex-A인지 자원이 제한된 Cortex-M인지 구분
2. **기준선 측정**: 정확도, 지연 시간, 메모리, 실행 파일 크기 기록
3. **최소 구성 선택**: 기존 런타임을 먼저 축소하고, 필요성이 입증되면 전용 실행기 고려
4. **동등성 검증**: 변환 전후 출력이 허용 오차 내에 있는지 테스트 데이터로 비교
5. **보안 검증**: 바이너리·실행 메모리에서 모델을 복구할 수 있다고 가정하고 보호 계층 설계

참고: [XNNPACK](https://github.com/google/XNNPACK) · [CMSIS-NN](https://github.com/ARM-software/CMSIS-NN) · [TensorFlow Lite Micro](https://github.com/tensorflow/tflite-micro)

## 남아 있는 위험과 대응 (Residual Risks)

| 남는 위험 | 함께 검토할 통제 |
| :--- | :--- |
| 바이너리·메모리 분석과 모델 복원 | 분석 비용 상승, 최소 권한, 디버거·덤프 제한 |
| 모델 교체·비인가 업데이트 | 서명 검증, 인증된 업데이트, 키 보호 |
| 추론 API 반복 질의·출력 분석 | 인증, 호출 횟수 제한, 출력 정보량 축소 |
| 공급망·서명 키 침해 | 의존성 관리, 빌드 환경과 키 운영 분리 |
| 부채널·물리적 디버그 접근 | 플랫폼별 위협 평가와 하드웨어 보호 |

- **출력 정보량 축소**: 클래스별 확률 대신 최종 라벨만 반환하여 모델 추출에 쓰일 정보를 줄임
- **공급망 공격**: 빌드에 쓰는 라이브러리·도구나 서명 키를 침해해 정상 경로로 악성 코드를 배포하는 공격
- **단독 대책의 한계**: 암호화, 코드 변환, TEE 중 어느 것도 모든 공격을 단독으로 막지 못함
- **선택 기준**: 제품의 자산 가치와 공격자 능력에 맞춰 대책을 조합

## 다층 방어와 핵심 정리 (Defense in Depth)

<!-- IMAGE [계층도] 시큐어 부트 -> 무결성 검증 -> 모델 코드화 -> 접근 제어 다층 방어 (img/18-defense-layers.png) -->

| 계층 | 수단 | 줄이는 위험 |
| :--- | :--- | :--- |
| 부팅 | 플랫폼이 지원하면 시큐어 부트 | 신뢰할 수 없는 소프트웨어로 부팅 |
| 저장 | 암호화, 키 분리 | 오프라인 파일 복사 |
| 배포 | 서명된 릴리스, 인증된 업데이트 | 변조된 모델 설치 |
| 실행 | 최소 권한, 덤프 제한 | 무단 프로세스 접근 |
| 모델 | 코드 변환, 런타임 축소 | 파일을 바로 열어 분석하는 공격 |
| 물리 | 케이스, 디버그 포트 보호 | 직접적인 물리 접근 |

- **시큐어 부트**: 부팅 단계마다 다음 단계 소프트웨어의 서명을 검증하여 서명되지 않은 코드의 실행을 막는 기능
- **XNNPACK·CMSIS-NN**: 성능 커널이며 모델 암호화·기밀성 기능은 없음
- **런타임 선택**: 새 런타임 구현보다 기존 런타임의 축소 구성을 우선 검토
- **모델 변환의 위치**: 추출 비용을 높이는 한 계층이며, 보안은 위협 모델에 맞춘 조합으로 설계
